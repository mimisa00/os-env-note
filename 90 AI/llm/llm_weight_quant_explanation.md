# LLM 權重精度與量化格式說明

> 注意：以下記憶體估算僅為「模型權重本身」的儲存空間，**不包含**推論時的 KV Cache、activation buffer、batch size 等額外開銷，實際部署時（尤其長 context 情境）所需記憶體通常會明顯高於下表數字。

## 一、浮點數精度（訓練與推論常見格式）

| 精度 | 位元數 | 說明 | 備註 / 注意事項 |
| --- | --- | --- | --- |
| **FP32**（單精度浮點數） | 32-bit（4 bytes/參數） | 常規高精度訓練使用，推論時記憶體開銷最大。10 億參數約需 4GB。 | 現今很少直接拿來做大模型推論，主要用於訓練或做為精度基準。 |
| **FP16**（半精度浮點數） | 16-bit（2 bytes/參數） | 主流訓練與推論格式之一，10 億參數約需 2GB。 | ⚠️ 動態範圍較小（僅 5-bit 指數），訓練時容易發生數值溢位/下溢，需搭配 loss scaling；「幾乎不損失準確度」主要適用於推論階段，訓練階段需謹慎。 |
| **BF16**（Bfloat16） | 16-bit（2 bytes/參數） | Google 開發，與 FP32 有相同的指數範圍（8-bit 指數），能有效防止大模型訓練時的數值溢位，是目前多數大型模型訓練的首選格式。 | 精度（尾數位元）比 FP16 少，但因動態範圍與 FP32 一致，訓練穩定性更佳。 |
| **FP8**（8-bit 浮點數） | 8-bit | 分為 E4M3、E5M2 兩種子格式，主要用於 H100/H200 等新一代硬體，加速訓練與推論。 | 屬於浮點量化而非整數量化，跟下方的 INT8 概念不同，不宜混為一談。 |

## 二、整數量化格式（主要用於推論／地端部署）

| 精度 | 說明 | 記憶體 / 效果 | 備註 / 注意事項 |
| --- | --- | --- | --- |
| **INT8**（8-bit 量化） | 將權重壓至 8-bit 整數。 | 10 億參數約需 1GB，能提升推論速度。 | 精度會有*輕微*損失（並非「維持高精準度」），對精度敏感任務（如數學推理）有時會有可觀察到的下降，通常需搭配校準（calibration）或 SmoothQuant 等技術降低誤差。 |
| **INT4**（4-bit 量化） | 目前地端部署常見的甜蜜點（Sweet Spot）。 | 700 億參數模型從 16-bit（140GB）壓到 4-bit 後，體積約降至 35GB，品質下降幅度通常可接受。 | **AWQ、GPTQ、EXL2、GGUF 並非精度格式本身，而是達成 4-bit（或其他 bit 數）量化的演算法/工具**，各自在校準方式、精度保留策略上有差異，不應與「INT4」並列成同一層級的「格式」。 |
| **INT2 / Q2**（2-bit 極端量化） | 極低 bit 壓縮技術。 | 能讓超大型模型（數百 B 參數）塞入消費級硬體，但誤差較大。 | 目前實務上較少直接用於正式生產環境，多用於研究或極端資源受限場景。 |

## 三、地端部署常見補充：GGUF 格式

地端部署（llama.cpp / Ollama 等生態）最常見的 **GGUF** 格式，內含多種量化變體，例如：

- `Q8_0`：接近 INT8 品質
- `Q5_K_M`、`Q4_K_M`：常見的精度/體積折衷選擇
- `Q2_K`：極端壓縮

這些變體讓使用者可以依硬體資源在「品質」與「體積/速度」之間彈性選擇。

## 四、實務估算提醒

- 表格中的 GB 數字 = **參數量 × 每參數位元組數**，僅代表權重檔案大小。
- 實際跑推論時，還需額外考慮：
  - **KV Cache**（與 context 長度、batch size 成正比，長文本時可能超過權重本身）
  - **Activation / 中間張量**
  - **框架本身的額外開銷**（CUDA context、buffer 等）
- 一般估算實際部署所需 VRAM 時，建議在權重大小基礎上再預留 20%–50%（甚至更多，視 context 長度而定）的緩衝空間。
